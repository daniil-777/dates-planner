# DEPLOY — path B: SAP BTP Cloud Foundry

The demo deployment. HANA Cloud instead of SQLite, XSUAA instead of HTTP basic auth, an
approuter in front, an MTA archive instead of a container.

**This is not the deployment that holds the receipts.** Read §0 before you spend an evening
on it.

Path A — `docs/DEPLOY.md`, Fly.io — is the daily driver.

---

## 0. The honest warning, first

**A free-tier SAP HANA Cloud instance stops itself every night.**

It is not a bug and there is no setting for it. A trial or free-plan instance is stopped
automatically once a day and has to be started again by hand from the BTP cockpit (or with
`cf update-service`/the HANA Cloud Central UI). Instances left stopped long enough are
deleted outright. So a household's shared expense app on the HANA free tier is a household's
shared expense app that is down every morning until someone opens a browser and presses
Start.

That is the whole reason this repository has two deployment paths. This one exists because
"SAP CAP app on BTP with HANA and XSUAA" is the thing the joke is *about*, and because it
is genuinely worth having proved that the same source runs there. Use it to show someone.
Use path A to actually track money.

**Nothing in this file has been executed.** It needs a BTP subaccount, entitlements, and a
HANA Cloud instance, none of which existed when it was written. Everything here is derived
from the repository's own configuration and from how `@sap/cds-dk` 10 generates these
files — the shapes are right, the specific service plan names and quotas in your
subaccount will differ, and the blocking issue in §6 is real and unresolved. Treat it as a
carefully reasoned plan, not as a transcript.

## 1. What changes, relative to path A

| | Fly (path A) | BTP (path B) |
|---|---|---|
| Database | SQLite on a volume | HANA Cloud, via an HDI container |
| Images | `LargeBinary` in that SQLite file | `BLOB` in HANA — see §5 |
| Auth | HTTP basic, two hashes in `srv/server.ts` | XSUAA + approuter — see §6 |
| SPA | served by `srv/server.ts` from `app/dist` | same, behind the approuter |
| Packaging | a Docker image | an MTA archive (`.mtar`) |
| Classifier | `ml/model/weights.json` in the image | same file, inside the `srv` module |
| Statement LLM | provider abstraction, any of four | same, and AI Core is a natural fit here |

The application code is identical. What changes is the persistence layer, the identity
provider, and the shape of the thing you upload.

## 2. Entitlements to add in the cockpit

BTP cockpit → your subaccount → **Entitlements** → *Configure Entitlements* → *Add Service
Plans*. Nothing below can be created until its plan is entitled to the subaccount, and the
error you get if you skip this is `Service offering 'x' not found`, which does not say so.

| Service | Plan | Why |
|---|---|---|
| **SAP HANA Cloud** | `hana-free` (or `hana` if you pay) | the database |
| **SAP HANA Schemas & HDI Containers** | `hdi-shared` | the schema the app deploys into. Separate entitlement from HANA Cloud itself; forgetting it is the most common first failure |
| **Authorization and Trust Management Service** | `application` | XSUAA — issues the JWTs the approuter forwards |
| **Cloud Foundry Runtime** | enough GB for two apps | `srv` ~1 GB, `approuter` ~256 MB. See §4 |
| **Document Information Extraction** | `default`, or `blocks_of_100` on trial | only if you want live receipt extraction; without it the app runs on the bundled fixtures |
| **SAP AI Core** | `extended` (`free` has no orchestration) | only if you want the statement generated by the generative AI hub rather than by the template |
| **Destination** | `lite` | optional. The approuter template references it; you can delete that resource if you use none |

Then, in the same subaccount, **Cloud Foundry Environment** must be enabled and you need an
org and a space:

```bash
cf login -a https://api.cf.eu10-004.hana.ondemand.com --sso
cf target -o <org> -s <space>
```

Create the database once, from HANA Cloud Central (cockpit → *SAP HANA Cloud*), not from
the CLI: the wizard is where you set the instance to allow connections from your CF space,
which is the setting people miss.

## 3. Generate the BTP scaffolding

From the repository root:

```bash
npx cds add hana,xsuaa,approuter,mta
```

That one command does four separate things:

* **`hana`** — adds `@cap-js/hana` to `dependencies` and a `cds.requires.db.[production]`
  block pointing at `kind: hana-cloud`. Your local SQLite configuration stays where it is,
  under the default profile, which is why `npm run dev` keeps working afterwards.
* **`xsuaa`** — writes `xs-security.json` (the scopes and role templates, derived from the
  `@requires` annotations already in `srv/*.cds`) and adds `cds.requires.auth.kind: xsuaa`
  under the production profile.
* **`approuter`** — creates `app/router/` with its own `package.json` and `xs-app.json`.
* **`mta`** — writes `mta.yaml`, wiring the three modules and three resources together.

Run it on a clean tree and read `git diff` before you commit any of it. `cds add` edits
`package.json`, and this project's `package.json` has hand-written `cds` configuration in
it that you do not want silently reshaped.

## 4. `mta.yaml`

What the generator produces, with the four edits this app actually needs. Comments marked
**[edit]** are the ones that are not generated.

```yaml
_schema-version: '3.2'
ID: twoway-match
version: 1.0.0
description: Two-Way Match — household date management

parameters:
  enable-parallel-deployments: true

build-parameters:
  before-all:
    - builder: custom
      commands:
        # [edit] The SPA is built into app/dist and served by srv/server.ts, exactly as it
        # is in the container. Without this line the srv module ships without a frontend
        # and you get a 404 at / with a working API.
        - npm --prefix app ci
        - npm --prefix app run build
        # cds build --production writes gen/srv (the CAP module) and gen/db (the HDI
        # artefacts: .hdbtable, .hdbview, and the CSV loader for db/data/*.csv).
        - npx cds build --production

modules:
  # ---------------------------------------------------------------- the service
  - name: twoway-match-srv
    type: nodejs
    path: gen/srv
    parameters:
      buildpack: nodejs_buildpack
      # 1 GB, not the 512 MB the Fly machine gets: @sap/hana-client is a heavier client
      # than the SQLite driver, and the classifier parses a ~5 MB weights.json at startup.
      memory: 1024M
      disk-quota: 2048M
    build-parameters:
      builder: npm
      ignore: ['node_modules/', 'default-env.json', '.env']
    provides:
      - name: srv-api
        properties:
          srv-url: '${default-url}'
    requires:
      - name: twoway-match-db
      - name: twoway-match-auth
    properties:
      # [edit] See §6. NODE_ENV=production activates the HTTP basic auth middleware in
      # srv/server.ts, which would 401 every request the approuter forwards — those carry
      # a bearer JWT, not an Authorization: Basic header. Until srv/server.ts learns to
      # stand down when auth.kind is xsuaa, this must NOT be set to production here, and
      # you lose HSTS and `trust proxy` with it. Read §6 before deploying.
      CDS_ENV: production

  # ---------------------------------------------------------------- HDI deployer
  - name: twoway-match-db-deployer
    type: hdb
    path: gen/db
    parameters:
      buildpack: nodejs_buildpack
      memory: 256M
    requires:
      - name: twoway-match-db

  # ---------------------------------------------------------------- approuter
  - name: twoway-match-approuter
    type: approuter.nodejs
    path: app/router
    parameters:
      keep-existing-routes: true
      disk-quota: 512M
      memory: 256M
    requires:
      - name: srv-api
        group: destinations
        properties:
          name: srv-api
          url: '~{srv-url}'
          forwardAuthToken: true
      - name: twoway-match-auth

resources:
  - name: twoway-match-db
    type: com.sap.xs.hdi-container
    parameters:
      service: hana
      service-plan: hdi-shared
    properties:
      hdi-service-name: '${service-name}'

  - name: twoway-match-auth
    type: org.cloudfoundry.managed-service
    parameters:
      service: xsuaa
      service-plan: application
      path: ./xs-security.json
      config:
        xsappname: twoway-match-${org}-${space}
        tenant-mode: dedicated
```

`app/router/xs-app.json` — the generated file plus one route, because this app's SPA and
its OData service are both served by the `srv` module:

```jsonc
{
  "welcomeFile": "/",
  "authenticationMethod": "route",
  "routes": [
    {
      // Everything: the SPA at /, the OData services at /ledger and /admin, /health.
      // authenticationType "xsuaa" is what makes the approuter bounce an anonymous
      // visitor to the login page before anything reaches CAP.
      "source": "^/(.*)$",
      "target": "$1",
      "destination": "srv-api",
      "authenticationType": "xsuaa",
      "csrfProtection": false
    }
  ]
}
```

`csrfProtection: false` because the SPA talks OData with its own client and does not fetch
an approuter CSRF token; leaving it on turns every POST into a 403. The service is still
same-origin-only (`srv/server.ts` refuses cross-origin requests outright), which is the
protection that actually matters here.

Build and deploy:

```bash
npm i -g mbt
mbt build -t ./mta_archives
cf deploy mta_archives/twoway-match_1.0.0.mtar
```

The first deploy takes ten to fifteen minutes, most of it the HDI container.

## 5. HANA and `LargeBinary` — read before the first deploy

`db/schema.cds` stores images in the database, not on a disk:

```cds
entity Receipts { image : LargeBinary @Core.MediaType: mediaType; … }
entity Photos   { image : LargeBinary @Core.MediaType: mediaType; … }
```

On SQLite that is a `BLOB` in a file you can copy. On HANA it is a `BLOB` in a column store,
and four things follow.

**1. `@Core.MediaType` is load-bearing, not decorative.** It is what turns the element into
an OData media stream, so the image is fetched by its own request
(`/ledger/Receipts(<id>)/image`) rather than being inlined as base64 in the entity payload.
Drop the annotation and every list read of `Receipts` drags every photograph across the
wire. Keep it. `srv/ledger-service.cds` projects `Receipts` with `*` precisely so the
annotation travels with the element and there is no second copy to keep in sync.

*Unverified:* whether CAP's HANA driver also excludes the BLOB from a plain
`SELECT * FROM Receipts` at the database layer, or fetches it and discards it. Check the
generated SQL with `cds.env.log.sql` before you assume list reads are cheap. On SQLite it
costs milliseconds; on HANA it costs memory you are paying for.

**2. You cannot filter, sort, index or group by a `LargeBinary`.** Nothing in this app does
— every query goes through `merchantNorm`, `date` or `category_code` — but it is worth
knowing before someone adds a "find the duplicate receipt image" feature.

**3. The first deploy generates `.hdbtable`; the second one has to migrate.** `cds build`
produces plain `.hdbtable` artefacts. HDI applies those by comparing structures, and a
change it considers destructive — a type change on a column that holds data, and a BLOB
counts — makes it refuse the deployment rather than drop the column. When that happens you
need `.hdbmigrationtable` for that entity, which is a manual conversion. The practical
advice: get `db/schema.cds` right before the first `cf deploy`, and take a copy of anything
you care about before any later schema change.

**4. Size.** HANA `BLOB` tops out at 2 GB per value, which is not the constraint;
`srv/lib/images.ts` normalises a receipt to tens of kilobytes. The constraint is the
instance. A free-plan HANA Cloud instance is small, and a few thousand receipts of
in-database images will make themselves felt long before the 30 GB of disk does. If this
ever became the primary deployment, images would move to an object store and the schema
would keep a URL — which is a real change to `db/schema.cds`, not a configuration switch.

One more, unrelated to blobs: **CSV seeding runs on every HDI deploy.** `gen/db` contains a
loader for `db/data/*.csv`, and HDI treats those files as the source of truth for their
tables. If you edit a partner's name through the app and then redeploy, HDI will put the
placeholder back. Move the identity rows out of the CSVs, or accept that a deploy resets
them.

## 6. Authentication — the blocking issue

`srv/server.ts` mounts HTTP basic authentication in front of every route when
`NODE_ENV === 'production'`:

```ts
const credentials = isProduction() ? loadCredentials() : null
…
if (credentials !== null) app.use(basicAuth(credentials))
```

and `loadCredentials()` **throws at startup** if `AUTH_USER_A` / `AUTH_HASH_A` /
`AUTH_USER_B` / `AUTH_HASH_B` are not four valid values. That is exactly right for path A,
where basic auth *is* the authentication. On BTP it is wrong in both directions:

* Set `NODE_ENV=production` and provide the four `AUTH_*` variables, and the app boots — and
  then rejects every request the approuter forwards, because those carry
  `Authorization: Bearer <jwt>`, not `Authorization: Basic …`. The XSUAA login succeeds and
  the app 401s anyway.
* Set `NODE_ENV=production` and omit them, and the app refuses to start.
* Leave `NODE_ENV` unset (`CDS_ENV=production` alone selects CAP's production profile, so
  HANA and XSUAA are still used), and everything works — but `isProduction()` is now false,
  so you also lose `app.set('trust proxy', 1)`, the HSTS header, and the tightened
  `connect-src`, and you gain `http://localhost:5173` in the CSP of a public deployment.

**The fix is one condition in `srv/server.ts`**, which is not this file's to change: basic
auth should be mounted when it is the configured strategy, not when the environment happens
to be production —

```ts
const usesXsuaa = cds.env.requires?.auth?.kind === 'xsuaa'
const credentials = isProduction() && !usesXsuaa ? loadCredentials() : null
```

— leaving `isProduction()` free to keep meaning "production hardening". Until that lands,
path B runs with `CDS_ENV=production` and `NODE_ENV` unset, and is a demo you show people
rather than an app you leave running. This is recorded in `GO-LIVE.md`.

Once XSUAA is doing the authentication, the roles come from `xs-security.json` and are
assigned in the cockpit under **Security → Role Collections**: create one, add the
generated role templates (`admin` at minimum — `srv/admin-service.cds` is
`@requires: 'admin'`), and assign it to both users. A user with no role collection sees a
403 from `/admin` and an app that otherwise works, because `LedgerService` has no
`@requires`.

## 7. Services, secrets and environment

Bind the two services (the MTA does this) and set the rest as user-provided environment.
`cf set-env` values are visible to anyone with `SpaceDeveloper` on the space — that is the
same trust boundary as `fly secrets`, but say it out loud rather than assume it.

```bash
cf set-env twoway-match-srv ANTHROPIC_API_KEY 'sk-ant-…'
cf set-env twoway-match-srv DOCAI_URL 'https://aiservices-dox.cfapps.eu10.hana.ondemand.com'
cf set-env twoway-match-srv DOCAI_UAA_URL '…'
cf set-env twoway-match-srv DOCAI_CLIENT_ID '…'
cf set-env twoway-match-srv DOCAI_CLIENT_SECRET '…'
cf restage twoway-match-srv
```

The full list of variables, with what each one buys, is `.env.example` and §4 of
`docs/DEPLOY.md`. The `AUTH_*` four are the only ones that differ between the paths: on BTP
they are not used at all.

On BTP the Document AI credentials can also arrive the proper way, through a service
binding — entitle *Document Information Extraction*, add it as a resource in `mta.yaml`,
and read the key from `VCAP_SERVICES` instead of from four environment variables. The
client in `srv/lib/documentai/client.ts` reads environment variables today
(`docs/CONTRACTS.md` §6), so that is a code change, not a configuration one. Listed here
because it is the obvious next step, not because it is done.

## 8. Afterwards

```bash
cf apps
cf logs twoway-match-srv --recent
cf env twoway-match-srv
cf ssh twoway-match-srv
```

Health check, once you have a session cookie from the approuter login:

```
https://<org>-<space>-twoway-match-approuter.cfapps.<region>.hana.ondemand.com/health
```

Same payload as path A. `docai`, `llm` and `model` are the three fields worth reading.

**Every morning**, until you move off the free tier: cockpit → SAP HANA Cloud → your
instance → **Start**. Then wait two or three minutes for the app to reconnect. If you find
yourself doing this more than a few times, that is the sign to go back to
`docs/DEPLOY.md` — which is the point this document opened with.
